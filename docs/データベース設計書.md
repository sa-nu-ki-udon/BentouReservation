# データベース設計書

## 1. 概要

弁当予約管理アプリケーションのデータベース設計書。
本設計は要件定義書に基づき、業者管理、メニュー管理、注文管理、集計機能に必要なテーブルを定義する。

### 1.1 使用データベース
- **RDBMS**: H2 Database (ファイルベース)
- **ORM**: Spring Data JPA (Hibernate)
- **DDL管理**: 自動生成 (`spring.jpa.hibernate.ddl-auto=update`)

### 1.2 設計方針
1. **論理削除**: マスタデータ（業者、メニュー、メニューセット）は物理削除せず、論理削除フラグで管理
2. **履歴管理**: メニューの価格変更は新レコードとして保存し、適用開始日で管理
3. **監査証跡**: 全テーブルに作成日時・更新日時を記録
4. **データ整合性**: 過去の注文データとの整合性を保つため、削除されたマスタも保持

## 3. テーブル詳細設計

### 3.1 vendors (業者マスタ)

弁当業者の情報を管理するテーブル。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | 業者ID (主キー) |
| name | VARCHAR(100) | NO | - | 業者名 |
| contact_info | VARCHAR(255) | YES | - | 連絡先情報 (電話番号、FAX番号等) |
| deleted | BOOLEAN | NO | FALSE | 論理削除フラグ (TRUE: 削除済み) |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 更新日時 |

**制約**
- PRIMARY KEY: id
- UNIQUE KEY: name (削除されていない業者名は一意)

**インデックス**
- idx_vendors_deleted: (deleted)
- idx_vendors_name: (name)

**備考**
- 想定データ数: 5社程度
- 論理削除されても過去の注文データとの紐付けを保持

### 3.2 menus (メニューマスタ)

メニューの情報と価格履歴を管理するテーブル。
価格変更時は新しいレコードとして登録する。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | メニューID (主キー) |
| vendor_id | BIGINT | NO | - | 業者ID (外部キー: vendors.id) |
| name | VARCHAR(100) | NO | - | メニュー名 |
| price | DECIMAL(10,2) | NO | - | 価格 |
| effective_from | DATE | NO | - | 価格適用開始日 |
| description | TEXT | YES | - | メニューの説明 |
| deleted | BOOLEAN | NO | FALSE | 論理削除フラグ |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 更新日時 |

**制約**
- PRIMARY KEY: id
- FOREIGN KEY: vendor_id REFERENCES vendors(id)
- UNIQUE KEY: (vendor_id, name, effective_from) - 同じ業者・メニュー名・適用開始日の組み合わせは一意

**インデックス**
- idx_menus_vendor_id: (vendor_id)
- idx_menus_deleted: (deleted)
- idx_menus_effective_from: (effective_from)

**備考**
- 想定データ数: 全体で20種類程度 × 価格変更履歴
- 価格変更時は新レコードを作成し、effective_from で適用開始日を管理
- 注文時点で有効だったメニュー・価格を特定するため、effective_from が重要

### 3.3 menu_sets (メニューセット)

メニューセットの情報を管理するテーブル。
複数の業者・メニューをまとめたセットを定義する。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | セットID (主キー) |
| name | VARCHAR(100) | NO | - | セット名 (例: レギュラーセット、休日出勤用セット) |
| description | TEXT | YES | - | セットの説明 |
| deleted | BOOLEAN | NO | FALSE | 論理削除フラグ |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 更新日時 |

**制約**
- PRIMARY KEY: id
- UNIQUE KEY: name (削除されていないセット名は一意)

**インデックス**
- idx_menu_sets_deleted: (deleted)
- idx_menu_sets_name: (name)

**備考**
- 1つのセットに複数業者・複数メニューを含むことが可能
- 論理削除されたメニューを含むセットも保持（過去データの整合性のため）

### 3.4 menu_set_items (メニューセット詳細)

メニューセットとメニューの紐付けを管理する中間テーブル。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | セット詳細ID (主キー) |
| menu_set_id | BIGINT | NO | - | セットID (外部キー: menu_sets.id) |
| menu_id | BIGINT | NO | - | メニューID (外部キー: menus.id) |
| display_order | INT | YES | 0 | 表示順序 |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 作成日時 |

**制約**
- PRIMARY KEY: id
- FOREIGN KEY: menu_set_id REFERENCES menu_sets(id)
- FOREIGN KEY: menu_id REFERENCES menus(id)
- UNIQUE KEY: (menu_set_id, menu_id) - 同じセット内に同じメニューは重複不可

**インデックス**
- idx_menu_set_items_set_id: (menu_set_id)
- idx_menu_set_items_menu_id: (menu_id)

**備考**
- 1つのセットに複数のメニューが含まれる (1対多)
- display_order で画面表示時の順序を制御

### 3.5 calendar_settings (カレンダー設定)

日付ごとのメニューセットと休日情報を管理するテーブル。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | カレンダー設定ID (主キー) |
| date | DATE | NO | - | 対象日付 |
| menu_set_id | BIGINT | YES | - | セットID (外部キー: menu_sets.id, NULL: メニュー未設定) |
| is_holiday | BOOLEAN | NO | FALSE | 休日フラグ (TRUE: 休日・注文不可) |
| memo | VARCHAR(255) | YES | - | メモ (休日の理由等) |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 更新日時 |

**制約**
- PRIMARY KEY: id
- FOREIGN KEY: menu_set_id REFERENCES menu_sets(id)
- UNIQUE KEY: date - 1日に1レコードのみ

**インデックス**
- idx_calendar_date: (date) - 日付での検索が頻繁に発生
- idx_calendar_menu_set_id: (menu_set_id)
- idx_calendar_is_holiday: (is_holiday)

**備考**
- 何年先までも設定可能（実運用では1～2年分）
- menu_set_id が NULL の場合はメニュー未設定
- is_holiday が TRUE の場合は注文不可
- 祝日出勤や平日休みにも対応

### 3.7 orders (注文)

社員の弁当注文情報を管理するテーブル。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | 注文ID (主キー) |
| employee_id | BIGINT | NO | - | 社員ID (外部キー: employees.id) |
| order_date | DATE | NO | - | 注文対象日 (弁当を食べる日) |
| menu_id | BIGINT | NO | - | メニューID (外部キー: menus.id) |
| price_at_order | DECIMAL(10,2) | NO | - | 注文時の価格 (価格変更に備えて記録) |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 注文作成日時 |
| updated_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 注文更新日時 (変更履歴) |

**制約**
- PRIMARY KEY: id
- FOREIGN KEY: employee_id REFERENCES employees(id)
- FOREIGN KEY: menu_id REFERENCES menus(id)
- UNIQUE KEY: (employee_id, order_date) - 1人1日1食のみ

**インデックス**
- idx_orders_employee_id: (employee_id)
- idx_orders_order_date: (order_date) - 日次集計で頻繁に使用
- idx_orders_menu_id: (menu_id)
- idx_orders_created_at: (created_at) - 月次集計で使用

**備考**
- 1日1食のみ注文可能（UNIQUE制約で保証）
- 注文対象日の当日朝8:30まで変更・キャンセル可能（アプリケーション側で制御）
- price_at_order に注文時の価格を記録し、価格変更の影響を受けないようにする
- 未来の日付への事前注文が可能
- レコードが存在しない場合は「注文なし」を意味する（物理削除でキャンセル）

### 3.8 billing_closing_dates (締め日設定)

業者別・個人別の請求締め日を管理するテーブル。

| カラム名 | データ型 | NULL | デフォルト | 説明 |
|---------|---------|------|-----------|------|
| id | BIGINT | NO | AUTO_INCREMENT | 締め日設定ID (主キー) |
| type | VARCHAR(20) | NO | - | 締め日タイプ (VENDOR: 業者別, EMPLOYEE: 個人別) |
| target_id | BIGINT | YES | - | 対象ID (業者IDまたはNULL) |
| closing_day | INT | NO | - | 締め日 (1～31、31は月末) |
| description | VARCHAR(255) | YES | - | 説明 |
| created_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 作成日時 |
| updated_at | TIMESTAMP | NO | CURRENT_TIMESTAMP | 更新日時 |

**制約**
- PRIMARY KEY: id
- CHECK: closing_day BETWEEN 1 AND 31
- UNIQUE KEY: (type, target_id) - タイプと対象IDの組み合わせは一意

**インデックス**
- idx_billing_type: (type)
- idx_billing_target_id: (target_id)

**備考**
- type = 'VENDOR' の場合: target_id は vendors.id（業者ごとの締め日）
- type = 'EMPLOYEE' の場合: target_id は NULL（個人請求の共通締め日）
- 締め日は固定値として運用（月によって変わらない）
- closing_day = 31 は月末を意味する

## 6. データ制約と設計方針

### 6.1 論理削除

以下のテーブルは論理削除を使用：
- vendors
- menus
- menu_sets
- employees

**理由**: 過去の注文データとの整合性を保つため

### 6.2 価格変更履歴

menusテーブルで価格変更履歴を管理：
- 価格変更時は新レコードを作成
- effective_from で適用開始日を管理
- ordersテーブルの price_at_order に注文時の価格を保存

### 6.3 注文制限

- 1人1日1食のみ（orders テーブルの UNIQUE KEY で保証）
- 注文対象日の当日朝8:30まで変更可能（アプリケーション側で制御）

### 6.4 カレンダー設定

- 1日1レコード（UNIQUE KEY で保証）
- menu_set_id が NULL の場合はメニュー未設定
- is_holiday が TRUE の場合は注文不可

### 6.5 締め日設定

- 業者別締め日: type='VENDOR', target_id=vendors.id
- 個人請求締め日: type='EMPLOYEE', target_id=NULL
- 締め日は1～31の整数（31は月末）

## 7. サンプルデータとユースケース

### 7.1 日次集計クエリ（イメージ）

``` sql
SELECT
  v.name AS vendor_name,
  m.name AS menu_name,
  COUNT(*) AS quantity
FROM orders o
INNER JOIN menus m ON o.menu_id = m.id
INNER JOIN vendors v ON m.vendor_id = v.id
WHERE o.order_date = '2025-01-15'
GROUP BY v.id, v.name, m.id, m.name
ORDER BY v.id, m.id;
```

### 7.2 個人別月次集計クエリ（イメージ）

``` sql
SELECT
  o.order_date,
  m.name AS menu_name,
  o.price_at_order AS price,
  SUM(o.price_at_order) OVER (PARTITION BY o.employee_id) AS total
FROM orders o
INNER JOIN menus m ON o.menu_id = m.id
WHERE o.employee_id = 1
  AND o.order_date BETWEEN '2025-01-01' AND '2025-01-31'
ORDER BY o.order_date;
```
